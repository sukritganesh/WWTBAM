# Proposed Commit Plan

This is a suggested review sequence for the existing implementation. It does not assert that these commits have been created, and it intentionally contains no commit hashes. Each step should include the focused tests for the behavior introduced in that step so intermediate revisions remain understandable and, where practical, buildable.

## Review guidance

- Keep generated catalog artifacts in the same review step as the pipeline that produces them, and verify a clean rebuild is byte-for-byte deterministic.
- Keep schema migrations with the repository behavior and fixtures that exercise them; do not separate a migration from its compatibility tests.
- Keep reducer changes with their transition tests, especially when a UI commit consumes a new action or phase.
- Treat the final integration step as orchestration rather than a place to hide subsystem logic. Rules, validation, persistence, and audio behavior should remain in their dedicated modules.
- If this plan is used to reconstruct history, avoid mixing formatting-only rewrites with behavioral changes; that makes the content hashes, generated artifacts, and persistence invariants easier to review.
